## How it is built

**Registry first.** `Command` holds name (`"company new"`), scope (`hub` or `company`), `writes` (bool), input model, output model, description (one sentence), error codes, and the function. `@command(...)` registers at import. The CLI is produced by iterating the registry: one Typer sub-app per noun, one command per verb, one option per input-model field, typed from the field annotation, with the field description as help. Nothing in `adapters/cli` names a specific command. Row 3, 4, and 9 reuse the same walk.

**Context.** The CLI builds a `Context` with `interface="cli"`, `client_name="bookflow-cli"`, `client_version` from package metadata, `client_host` from the hostname, a fresh `session_id` per invocation, a fresh `request_id` per command, and the actor from `config.toml`'s OS-user mapping or from `--as-token`. `reason`, `directive_id`, `source_ref`, `idempotency_key` are accepted as global options and carried; row 2 enforces them. Any input model that declares a field named like a context field fails registration.

**Data root.** Resolution order: `--data-root`, `BOOKFLOW_DATA_ROOT`, `~/.bookflow`. `init` creates it with `hub.db`, `config.toml`, and `companies/`. Running any other command against a root without `hub.db` returns `E_NOT_INITIALIZED`.

**init.** Runs hub migrations, creates the `system` user, creates one human user (username from `--username`, default the OS login name; display name from `--display-name`), writes the OS-user to Bookflow-user mapping into `config.toml`. Passwords are not set in row 1; row 7 adds `user set-password`. `init` on an initialized root is a no-op that reports the existing state.

**company new.** Input model is every field of blueprint 9.1 except `closing_date`, plus `--chart` (validated against the seed directory, stored in `default_chart`, applied in row 5). Steps, in one function with cleanup on failure: derive the folder name (below); create the folder and `attachments/`, `backups/`, `exports/`; write `bookflow-company.toml` with id, display name, schema version; create `company.db` and run company migrations; insert the `company_info` row; register the company in hub `companies` with its path; insert the owner membership for the actor. Failure after folder creation removes the folder. Output: `company_id`, `display_name`, `path`.

**Folder naming.** Take the display name; replace `/ \ : * ? " < > |` and characters below U+0020 with a space; collapse runs of whitespace; strip leading and trailing spaces and dots; truncate to 100 characters; if empty, use `Company`; if the result, case-insensitively, is a Windows reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`) append ` Co`. If the folder exists, append ` (2)`, ` (3)`, and so on, comparing case-insensitively. Non-ASCII letters are kept.

**company list, show, update, rename, use, attach, delete.** `list` returns companies where the actor has an unrevoked membership, sorted by display name. `show` returns hub registry fields plus the `company_info` row. `update` changes any `company_info` field except `home_currency` and `closing_date`, increments `version`, and sets `updated_*`. `rename` changes `display_name` in hub and info, and with `--move` renames the folder using the naming rule and rewrites the hub path. `use` writes `default_company` to `config.toml`. `attach <path>` reads the marker file, refuses if the id is already registered (`E_ALREADY_ATTACHED`), registers the path, and grants the actor owner membership. `delete` requires `--confirm <company_id>` matching, removes the registry row and memberships, and removes the folder; `E_CONFIRM_MISMATCH` otherwise.

**Company selection.** `--company` accepts an id or a display name; a display name matching more than one accessible company returns `E_COMPANY_AMBIGUOUS`. Then `BOOKFLOW_COMPANY`, then `default_company`. An inaccessible or nonexistent company returns `E_COMPANY_NOT_FOUND` in both cases.

**Versioning columns.** Every table created in row 1 carries the blueprint 6.1 fields. `update` increments `version`. Conflict semantics, presence, idempotency replay, and the audit tables are row 2 and are not created here.

**Engine.** One SQLAlchemy engine per open database, `PRAGMA journal_mode=WAL`, `PRAGMA foreign_keys=ON`. Before opening `company.db`, `engine.py` checks the mount type of its path: on Linux, a path under a mount of type `nfs`, `nfs4`, `cifs`, `smb3`, `smbfs`, `fuse.sshfs`, or `9p` in `/proc/mounts` is refused with `E_NETWORK_SHARE`; on other platforms or when the mount table is unreadable, the check passes. Migrations run under an exclusive `company.db.lock` file taken with `fcntl`/`msvcrt`; a second process waits up to 30 seconds then fails with `E_MIGRATION_LOCKED`. Before migrating an existing database, a copy is written to `backups/<YYYY-MM-DD-HHMMSS>.db`.

**Schema version.** Both databases use Alembic's `alembic_version` table. The company marker file repeats the version for `attach` to read without opening the database. Opening a database whose version is unknown to the code returns `E_SCHEMA_TOO_NEW`.

**demo reset.** Reads `demo/seed.toml`, deletes any registered company with the seed's display name whose marker file carries `demo = true`, and runs the same rollout function as `company new`, then writes `demo = true` into the marker. Row 1's seed holds company info only.

**Money.** `Money` is built now because `company_info.home_currency` validation needs the currency table (ISO 4217 code and decimal places). Parsing and formatting are tested; nothing posts yet.

**CLI output.** Without `--json`: `list` renders a table of the output model's rows; `show` renders field per line; writes print the output model's identifying fields. With `--json`: the output model as one JSON object. Errors: JSON to stderr, exit codes per blueprint 5.4.

## Edges

- Nothing exists before this row; it touches nothing.
- Not built here and must not be faked: audit tables, conflict detection, presence, idempotency (row 2); HTTP, workbench (row 3); documentation generation (row 4); chart seeding and every list (row 5); notes and attachments (row 6); passwords, tokens, roles, and permission checks beyond "membership required to see a company" (row 7). Descriptions and error lists are filled on every command so row 4 has nothing to backfill.
- Row 2 will add audit writes inside the same service functions that row 1 creates; those functions take the `Context` now so row 2 changes no signatures.
- `uv` is not installed on the build machine; installing it is the first build step and is not part of the product.

## Verification the builder will perform

`pytest` green with the parity test covering every registered command. Then by hand: `bookflow init`, `bookflow company new` twice with the same name, `company list --json`, `company show`, copy the folder to a second data root, `company attach`, `company show` there, and `demo reset` twice.
