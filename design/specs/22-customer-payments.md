## 1. Owning outcome and boundary

A human or authorized program can record new customer cash, distribute it among parent/job invoices, retain unapplied AR credit with an explicit owner, apply that existing compatible credit later, correct either document, inspect settlement history, unapply and void. All operations use the same registry, permissions, identities, exact accounting and immutable audit history through CLI, HTTP and browser. An agent creates work that a person can inspect/continue in the GUI and vice versa. No UI-only allocation or agent-only correction implementation qualifies as complete.

Immediate interfaces are actual CLI, HTTP and workbench. `docs/agent-guide.md` expressly states MCP is absent. Row9's separately reviewed MCP adapter must later expose these same registered commands/models; attach a same-registry journey when Row9 lands, without inventing an endpoint, tools or agent-identity bootstrap today. Row22 completion must state this dependency honestly.

Implemented scope is home-currency, service-invoice customer receipts with one compatible AR account per payment; one payer can fund selected invoices in its current descendant family. Existing invoice/sales-receipt/work billing behavior remains. Payment is NOT a sales receipt and posts no revenue. Existing invoice-date tax liability postings remain; allocating receipt cents to tax does not enable the currently rejected payment-receipt tax-liability policy. Refunds, customer credit memos, discounts/writeoffs, liability-held advances, cross-job old-credit transfer, bank deposits/reconciliation/bounced checks, providers, card credentials, foreign-currency settlement, transaction deletion, statements/aging and full cash-basis reports remain separately staged features. Their reference controls are inventoried but not advertised as working buttons. Recording a payment is recording supplied cash facts, not proof a provider charged or a message was sent.

## 3. New cash derivation and permanent ownership

Receive inputs express payer plus invoice amounts, never posting buckets. Payer can be any active customer/job. Eligible new-cash invoices belong to that exact party or its current descendants; this recursive rule handles nested jobs consistently with the existing hierarchy. All selected invoices must share the payment AR account and home currency. At receipt, authorize and capture each invoice's actual party and relevant family lineage; a renamed/reparented invoice cannot silently change a previously previewed allocation.

For received positive integer M and positive selected amounts x[i]:

    C[party] = sum(x[i] for selected invoices owned by party)
    R = M - sum(x[i]); require R >= 0
    C[payer] += R

Merge equal party/AR/currency keys; omit zero components. Post one Dr destination M and one Cr AR for each positive C, carrying the exact party ID (`name_type=customer` also for jobs). No revenue or balancing plug. Residual is always the chosen payer's credit; preview and receipt explicitly name that owner. Parent invoices plus residual use one parent component.

After commit, each component's party/AR/currency is immutable. Existing application consumes only the component matching its invoice. Unapply releases credit to that same component. No matching component means no usable credit for that invoice even if the total payment/family balance is positive. A new receipt's calculation never includes prior credits. A payment amount is new recorded receipt money; old-credit application is a distinct action.

Example cents: parent invoice100, A600, B400; receive1000 selecting parent100/A600/B200. Credits parent200/A600/B200; parent residual100. After receipt, exact AR parent=-100/A=0/B=200, family100. Unapply A600 releases A600 without changing AR. Applying it to B is rejected; another A invoice can use it. A separate transfer would require balanced reclassification and is not implemented here.

Single AR account is a justified initial limit: no implicit offset of incompatible control accounts. `ar_account` may be explicitly selected; otherwise resolve the existing system accounts_receivable role. Grid filters to it and explains excluded incompatible invoices. Destination accepts active home-currency bank accounts and the actual system Undeposited Funds account; never accept arbitrary assets as cash. Reparenting affects current family aggregates/pickers, not immutable receipt ownership. Subsequent reuse checks exact component party regardless of later ancestry; historical detail retains captured family facts and separately shows current names.

## 4. Public commands and strict input models

All models forbid unknown fields, floats, booleans as money/versions and explicit null for non-nullable fields. Money is existing exact decimal text or typed `{minor_units,currency}` with consistency checks, home currency only, positive where specified, signed-64-bit persisted bounds and unbounded checked intermediate arithmetic. Dates use existing strict date type. Text/number limits reuse sales conventions (number existing `_Number`; memo2000; payment reference128). Versions are positive integers. Duplicate invoice/application/version IDs reject. User-selected write lists have explicit maximum200; reads page at50, maximum200. Server-derived correction dependencies are complete regardless of count and use the dependency guard below. No batch silently truncates.

Every new payment write requires `operation_key` (ASCII `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`), plus optional `expected_facts_fingerprint`. Common reason/directive/on-behalf metadata stays in existing authorized Context, not spoofable input fields. `--dry-run` is available for every write. Updates/void/unapply require a nonblank reason <=140; receive/apply accept optional reason. Dry run requires the key so preview and attempted commit have the same durable intent, but reserves nothing.

## 5. Preferences and selection behavior

Append three non-null strict Boolean company preferences across new/show/update and settings forms:

- `automatically_apply_payments=false`;
- `automatically_calculate_payments=false`;
- `use_undeposited_funds_for_payments=true`.

These initialized values are deliberate project defaults, not an assertion about an installation shown in the manual. Omission on update preserves; null/string/0/1 API inputs reject. All three are editable independently under existing company authority, with exact field provenance/conflict behavior.

The first preference controls suggestions in the new-payment form after customer/date/received amount are known. Suggested allocation first chooses one eligible invoice exactly matching the entered amount; ties by invoice accounting date then binary ID. Otherwise walk oldest invoice date then ID, applying min(due, unassigned receipt) until exhausted. Existing-credit suggestions additionally cap by the matching source component. Never mix prior credits with new received money. Save always sends the explicit reviewed list; the core receive command does not auto-select absent applications.

The second preference concerns selecting a grid invoice: when enabled, selection fills min(due, unassigned explicitly entered receipt/component credit); when disabled, user enters Payment amount. It never manufactures or silently changes `amount received`. If received amount is blank, the form can offer a clearly labelled “Use selected total as received amount” action; only that explicit action writes the proposed amount and requires ordinary preview. UI and agent `payment suggest` share the same integer resolver. Explicit user edits take precedence over suggestions. Recalculation on stale facts requires visible user acceptance/repreview; never silently shrink a typed allocation or switch exact-match invoice.

When UF preference is true and destination omitted, resolve UF; GUI hides the ordinary destination chooser but displays resolved UF in preview. An explicit API destination is still allowed as an intentional override and is shown as such; GUI offers “Choose another destination” to express that override, so the command is not more capable than the human flow. When false, show bank/UF picker and require destination if omitted. Store captured effective choices in receipt profile. Inactive unchanged method snapshots remain renderable/correctable without refresh; new/changed assignments must be active. New financial posting account references must be eligible and active, following existing sale checks.

Fingerprint policy is per command, not whole company version: receive reads UF policy only when destination omitted, effective method chain only when method omitted, selected hierarchy, invoice/payment versions/capacities, exact commercial inputs and custom definition facts. Explicit choices ignore unrelated preference changes. Suggestion output names settings it used; a commit with explicit selections does not depend on an unused auto-apply setting. Existing apply/unapply has no preference dependency. Settings/recommendation change details use audit evidence, never attribute all stale facts to the latest company writer.

## 7. Deterministic allocation and restatement

For target invoice, eligible components are every positive service net and positive per-line tax component; zero components remain valid commercial facts but receive no monetary allocation row. Current tax groups require distinct tax items, so logical component key is `(settlement line ordinal, kind 0 net / 1 tax, binary tax_item_id or empty)`. Use physical IDs only as provenance. Account/agency/rate/taxable/net facts are part of semantic identity comparison, not tie order; invoice line display order, regenerated row IDs and unrelated display-only labels are not.

For requested A, remaining capacities c and T=sum(c): q=(A*c)//T, r=(A*c)%T. Award A-sum(q) cents by descending r then logical key. No floats/rounding acceptance/zero rows. Full settlement consumes exact residue. Normal apply uses all existing committed active allocation capacity, including future effective dates, and never reshuffles prior applications merely because the new date is earlier. Any historical projection must still have nonnegative per-component capacities under the resulting dates; reject incompatible date/capacity input instead of recomputing old allocations silently.

Preview keys for retained lines are saved ordinals. New line occurrences get deterministic provisional ordinals above historic max in submitted order, including duplicate identical lines. Commit independently resolves the same occurrence recipe, allocates fresh ULIDs and attaches those ordinals; no ID reservation/cache reuse/deterministic-ULID hack. Fingerprint includes canonical intent, owned current versions, active applications and component facts/capacities, and the resulting logical allocation recipe, excluding transient row IDs/event IDs/timestamps. Key IDs created on first application/new component similarly map from deterministic semantic keys. A fingerprint verified on two previews and commit must predict exact cents by logical component.

On applied invoice semantic edit, recompute the COMPLETE surviving applications in `(effective_date, binary application_id)` order against the revised component capacities. Compare each proposed full split/facts with its live allocation set. Changed applications append exact inverse of all old live allocation rows and full replacement; unchanged applications retain allocation rows, even if they reference an older physical invoice revision. Current capacity follows stable logical keys, never only current_revision_id. Display current provenance separately from retained historical effect. Adding/removing/repricing lines or changing tax rules can change the denominator for otherwise unchanged lines, so compare complete splits, not just edited component IDs. Reordering retained lines alone preserves keys and splits.

Every changed/restated application keeps original ID, amount, source component, effective date; application rows themselves are not reinserted. Check every original allocation date against closing date. Missing/ambiguous physical attribution is validation failure, never invented revenue. Payment correction (§8) restates source provenance without recalculating the target split, avoiding propagation to unrelated payments on the same invoice. Later unapply reverses the exact CURRENT live allocation rows, not a fresh computation of the original split.

## 8. Corrections, versions and conflict diagnostics

Header versions are concurrency tokens, not commercial revision numbers. Each command bumps each affected payment/invoice header once, with a full attributed transaction audit before/after snapshot and ordinary update action; commercial revision increments only when commercial receipt/invoice content changes. Apply/unapply changes no document revision, no GL batch and no work header. Receive payment starts version1 and increments each selected invoice once. An invoice correction plus its allocation restatement is one invoice bump, and each payment whose allocation changes bumps once. Payment correction plus restatement is one payment bump, each affected invoice once. Pure no-op writes preserve headers/revisions/GL/audit, apart from a first-time operational retry receipt as §6 declares.

Row21 conflict lookup remains audit-header based and conservative. Extend sale/payment enrichment with **actual attributed settlement history**: report `settlement.applied`/`settlement.allocations` when corresponding application/attribution events occurred since a validated expected header; include event IDs and actor/on-behalf/interface/time in a separate settlement_changes collection. Preserve latest-writer wording and unknown/future history; never infer settlement from a bare version bump. Missing history still reports unknown. A stale invoice commercial editor seeing a new payment must reject and retain its draft, even when the commercial revision is unchanged. New payment commands require versions; unaffiliated legacy sale blind policy is unchanged.

Invoice edit: positive gross must cover all committed active applications; party/AR/currency unchanged while applications survive, and new date cannot exceed earliest application date. Fail E_APPLIED_EXCEEDS_TOTAL or E_HAS_APPLICATIONS. Existing old/new posting-date locks remain. Existing work-linked line/proof/receipt invariants remain before and independently inside validation. For actual changes requiring settlement recomputation, require `settlement_versions` covering exactly every active source payment OR the complete `settlement_guard`; authorize all first. If recomputation finds a payment unchanged, validate its version through the selected mechanism but do not bump it. The complete set prevents a phantom new application between preview/commit. A truly identical invoice no-op needs no additional payment tokens and preserves ordinary behavior.

Payment update is useful but explicitly bounded:

- Editable number/reference/memo, payment method, destination, accounting date, received amount and typed custom fields. Keep payer, AR, currency and non-payer component amounts fixed. An accidental different payer/job split requires explicit unapply → void erroneous receipt → receive corrected record with a new key/reason; closed dates may prohibit it. This is a correction workflow, not an advertised transfer of valid existing credit.
- Amount delta changes only the payer component. Its resulting amount must be nonnegative and cover its own active applications; total must remain positive. Example parent receipt with A600/B200 and parent200 can decrease to900 if parent applications<=100, but cannot decrease by borrowing A's released credit. A payer-only receipt can freely increase/decrease subject to its applied floor. Increasing old recorded cash is a correction; another remittance uses receive. This protects immutable job ownership without forcing ordinary memo/date/bank/amount fixes through void.
- Preserve old snapshots unless a changed method/destination/custom definition must resolve; captured payer identity can refresh only via a separately explicit future mechanism, not an accidental current-master rename. Date must remain <= every application date and old/new accounting dates open.
- Follow existing immutable sale correction shape for any actual receipt content revision: exact old batch reversal plus new balanced replacement, real revised receipt facts, same stable source keys. This is a real commercial correction, never a revision created solely for settlement version alignment. Changed source physical attribution causes full inverse/replacement allocation attribution for active applications at original dates, retaining their target splits and IDs. Require exactly all active target invoice versions OR the complete settlement_guard, authorize them and bump each once. If no active applications, no invoice tokens. Independently validate source/target totals and ownership after correction. A no-op creates no commercial revision/batch.

Invoice void rejects active applications. Payment void rejects active applications; explicit unapply first is required, then exact old-date inverse. Unapply uses original dates, not a convenient current date. Matching durable replay of any prior operation runs before current eligibility/version/closing-date checks (after current authority), so it remains inspectable after void/closure/settings changes and performs no new effect. A new operation key requests a new action and cannot bypass current restrictions.

## 9. Permanent operations versus ordinary retries

All payment writes require durable operation_key, company-wide across verbs, actor-independent so an authorized human and program can safely share the SAME intent. Current authorization is always applied to saved owned targets before replay/mismatch details; possession of a key grants nothing. A caller without required linked-work access gets uniform denial, not existence, balances or previous actor data.

Canonical request version1 hashes validated explicit input with defaults represented as omissions, command and selected company, and audited reason for commands requiring one. Normalize exact money and stable syntax; preserve ordered lists where occurrence order is meaningful. Exclude expected_facts_fingerprint and operation_key itself; INCLUDE requested expected versions, original selectors and all business changes. Store original canonical request plus resolved IDs/effect once. For matching replay, use saved IDs for authority and receipt reconstruction so renamed selectors or inactive master defaults do not force re-resolution. A changed intent under the same key returns E_PAYMENT_OPERATION_KEY_REUSED without effects. Failed validation, stale preview and preview itself reserve no key; a corrected draft may reuse its key until first successful commit. After success, edits require a new key.

Permanent lookup belongs in input authorization (to select saved owned targets safely), in normal planner before fresh-fact resolution, and in validator/persister under lock. Replay returns immutable original `effect` plus newly authorized `current`, with `idempotent_replay=true`, `changed=false`, `new_effect=false`; it never rewrites the operation receipt. Original effect has `changed` describing the original operation separately.
