## 1. Architecture and preserved authority

One client-launched stdio process exposes bookflow_list_commands, bookflow_help and bookflow_run using one configured existing Bookflow bearer. It talks to the existing host through bearer-authenticated /adapters/mcp bridge endpoints. The host retains the root lock, writer queue, readers, command registry, accounting engine and audit. The adapter does not start another host, acquire a bookkeeping root lock, invoke shell/CLI commands, or authenticate as its OS login.

Extract a shared hosted executor from adapters/http/app.py, calling core.dispatch.execute, and shared current-credential/publication guards. Use this for HTTP, workbench and the MCP bridge. Binary execution uses core.transfers.HostedTransfer, InputBody, TransferLease and existing command transfer.prepare/validate_resource, not a second attachment store or simulated JSON post. Add bridge operations for leased byte input/output and complete JSON result delivery, described in §6. All permission checks are shared command checks; transport handles never grant company/command access.

The host's dedicated MCP entry fixes interface=mcp. Existing HTTP stays http even if a caller sends an interface header or client label "mcp". Current human workbench activity remains interface=http, client_name=bookflow-workbench; do not claim interface=gui. MCP attribution names the adapter entry, not proof that a model originated the request. Direct invocation of this bearer-authenticated bridge has the same permissions and attribution. No caller-supplied actor/interface/principal override and no fallback to the ordinary HTTP route (which would misattribute MCP work).

Normal routed commands, including authorized token issue and user set-password, retain their exact rights, inputs, previews and outputs. No secret_io exclusion, silent secret removal, or transfer exclusion exists. Existing local_only/standalone and CLI --interactive/--follow lifecycle boundaries remain explicitly documented; they are not new MCP business denials. Native OAuth/Streamable HTTP MCP, prompts, sampling, elicitation, tasks, subscriptions and external sends remain outside this plan. The native bridge is Bookflow HTTP; it does not claim MCP OAuth compliance.

## 2. Verified protocol and SDK choice

Do not add the unrelated standalone `fastmcp` distribution or copy v1 decorators/imports. GitHub's latest release and PyPI both report 2.1.1, published 2026-08-25, non-prerelease. The current official protocol is **2026-07-28**, not the older initialization-only protocol. [Official release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.1.1), [published package](https://pypi.org/project/mcp/2.1.1/), [current specification](https://modelcontextprotocol.io/specification/2026-07-28).

Choose SDK v2's low-level `mcp.server.Server` with its typed list/call handlers and SDK stdio runner. This is justified by exact registry schemas and explicit `CallToolResult` construction: Bookflow errors must retain their complete JSON document in structured content. The low-level server does not validate tool arguments automatically; validate the three envelopes explicitly with Pydantic, then let dispatch validate the selected command input. SDK Python fields use snake_case, while the SDK handles wire aliases/era differences. Do not handwrite framing or version negotiation. [Low-level API](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/).

Support and test modern `server/discover`/per-request metadata and the SDK's legacy `2025-11-25` initialize path against the same three tools. Advertise the three tools with no list-change promise; chunk transfer controls are a separate envelope branch of bookflow_run, not extra tools. No dependence on legacy session identity for Bookflow authorization. STDIO stdout contains only protocol messages; diagnostics go to sanitized stderr, and EOF initiates exit. [STDIO binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [SDK legacy compatibility](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/).

STDIO credentials come from launch environment, which the protocol explicitly distinguishes from HTTP OAuth. Because the only MCP-facing transport here is stdio, do not advertise Bookflow's opaque token as an OAuth access token or claim MCP HTTP authorization compliance. Adding native Streamable HTTP would require a separately reviewed OAuth/resource-audience design. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

The published SDK requires Python>=3.10, Pydantic>=2.12, AnyIO>=4.9 on Python3.12, and `httpx2>=2.5.0`; Bookflow requires Python>=3.12 and currently locks Pydantic2.13.5/AnyIO4.15.0. Use `httpx2.AsyncClient` for the bridge, declare it explicitly in the MCP extra if imported directly, and pin the resolver-selected version in the lockfile. Verify its installed API in the isolated build environment. Keep existing HTTP test dependencies unchanged unless resolution requires a demonstrated adjustment. No SDK import during ordinary CLI startup or host startup; the pure JSON bridge does not need the optional SDK. Do not configure SDK OpenTelemetry exporters, auto-instrumentation or telemetry providers.

## 4. Standalone launch, configuration, company and provenance

Install the optional extra, start the intended host separately, inject a secret through the client's environment facility, then launch an absolute executable without a shell:

    /absolute/venv/bin/bookflow mcp --url http://127.0.0.1:8765 --token-env BOOKFLOW_TOKEN --client-name bookflow-agent

--url overrides BOOKFLOW_URL; --token-env names a variable and defaults to BOOKFLOW_TOKEN. No secret argv flag, token URL, credential in tool arguments, password prompt, automatic token issuance or OS-login fallback. Read the secret once; rotating it requires restart. A client must explicitly inject the variable if its subprocess launcher filters inherited environment; do not assume ${...} interpolation in client JSON. The installed guide supplies the exact supported client configuration and SDK subprocess environment construction.

One private HTTP client, fixed origin, trust_env=False, redirects/retries/proxy inheritance disabled, no cookies, verified TLS; plaintext only numeric loopback. Reject URL userinfo/query/fragment before reading/sending credentials. Never fetch a source_ref, schema $ref, attachment filename or model-supplied URL. No SDK telemetry/exporter configuration. Missing SDK or missing/empty launch token, malformed launcher options (not deferred company-selection config), or invalid launch values fail before protocol startup: nonzero process exit, safe stderr, no stdout. --help needs neither SDK nor root. A syntactically configured but invalid/expired token, stopped host or incompatible bridge does NOT kill startup: SDK discovery/tool listing works, and tool calls return structured configuration/auth errors. A restarted host can therefore recover without restarting the adapter; a changed token requires adapter restart. Contract compatibility is checked before each first submission to a host generation, not as a mandatory startup connection.

Register a lazy standalone launcher with protocol-owned stdout: no ordinary result renderer on EOF, no JSON receipt after the last MCP frame. Its output lifecycle descriptor is explicit and valid only for standalone commands. Reject inapplicable launch dry-run, interactive, reason, company and JSON-render flags with E_USAGE; do not confuse a process's configuration with a business command call. EOF/SIGTERM stops adapter admission and closes its HTTP work, not the Bookflow host.

### Company fallback (F3)

For each company-scoped execution: non-null company tool argument first; otherwise nonempty BOOKFLOW_COMPANY from the **stdio launcher's machine/process**; otherwise default_company for its actual OS login from that machine's selected Bookflow config. Use the same extracted selection helper and source labels option/env/default/none as CLI/Python. A present higher-precedence value that fails resolution never falls through. Hub-scoped calls ignore environment/default selection but reject an explicit non-null company.

The launcher accepts --selection-root solely for the fallback's read-only configuration source; precedence is that option, launcher BOOKFLOW_DATA_ROOT, then the same platform default used by CLI. It creates nothing there, acquires no writer/root lock, migrates nothing, and opens no company database. Use Config.load's existing read-only pending-projection handling where applicable. This narrow local config read replaces the earlier draft's blanket "no data root reads" claim. A missing config/mapping supplies no default; malformed/unreadable config returns shared E_CONFIG_INVALID only when that fallback is actually needed. Read the fallback per call, so an operator's local company use change is observed. Remote host environment, host service OS login and host default company never supply the remote MCP caller's implicit selection.

Local OS mapping supplies a selection preference only, never authentication. Even if it belongs to a more privileged local human, the selected company must resolve on the remote host under the bearer. Preserve ambiguity/not-found/visible-only suggestions and details.source. Unknown or hidden local defaults cannot grant remote access. Explicit company bypasses unnecessary local config reads. Frozen command/transfer preparation stores the selected company and source for that operation; a later environment/default change cannot redirect its chunks or execution. Test distinct caller/host defaults and roots, absent config, malformed fallback and high-precedence inaccessible selection.

### Process and client provenance (F5,F15)

Generate one fresh ULID at stdio process start and use it as Bookflow session_id for every command it initiates. Two processes with one token and a restart must have different sessions. Keep credential token ID separately in the host's internal authentication record; never use it as the MCP process session. Generate a fresh request_id on the host for each actual command execution; chunk/status calls are transport activity, not extra business executions/audit events.

client_name is the configured launcher label, client_version its installed package version, client_host the launcher machine hostname. The launcher sends these and its process session through a fixed versioned provenance envelope/header set, separate from model tool arguments. Host validates types/lengths and normalizes this informational metadata. It is self-reported client provenance, not an authenticated machine identity; direct HTTP bridge callers can claim labels/session strings and gain no rights. Credential/principal/company authorization, handle ownership and replay protection must never depend on trusting those labels or session IDs. MCP peer clientInfo remains informational and does not replace the configured Bookflow label. Interface is always constructed by the host route, never taken from provenance.

## 5. Exact three-tool and context contract

list_commands: optional prefix, limit integer1..200 default100, cursor. Returns deterministic command descriptors, next_cursor, registry_digest and bridge_version. help: required canonical command; returns the single-command generated documentation, full input/output schemas with local $defs, field descriptions, examples, command+infrastructure errors and accepted context/lifecycle/transfer metadata. Live host registry/renderer supplies both, not a local cache or scraped docs. Extract a pure single-command renderer from _command_page and share descriptors with docs/OpenAPI where fields coincide.

Catalog/help are authenticated static product metadata, the same for all valid tokens. They contain no real examples, company identifiers, principal names, paths, runtime options or per-company permission verdicts. Descriptions of required authority are not a can_run promise. Runtime choices come from authorized commands. Protocol tools/list itself may expose the three static schemas without contacting the host; no business data is in them. No mutable selected company is held by the MCP protocol connection beyond the explicit launcher preference fallback above.

bookflow_run has a discriminated envelope: ordinary command execution (default branch) or a transport-control branch (§6). Ordinary arguments are command, input (object or sealed input_ref, exactly one), company/reason/directive/source_ref/idempotency_key, dry_run, and optional response delivery preference. Canonical command names use spaces; no NLP, fuzzy command choice or private alias system. Transport controls never add fields to the registered input model. Validate both envelopes before using fields; unknown top-level keys are E_USAGE, invalid declared values E_VALIDATION, and Context fields inside business input E_CONTEXT_IN_INPUT. No permission or command execution is inferred from tool annotations; run is conservatively potentially destructive.

Presence rules are normative and implemented by a shared command-context normalizer, not serializer defaults:

| Argument | Omitted | Explicit null | Other supplied value |
|---|---|---|---|
| input | E_VALIDATION unless sealed input_ref used | E_VALIDATION | Must decode to object; preserve nested null/false/[]/{} exactly. |
| company | Use fallback for company commands | Same absence/fallback | Strict string; empty string remains an explicit failed selection, not fallback. On hub command E_USAGE. |
| dry_run | Effective false | E_VALIDATION | Strict boolean; false is inactive on every kind, including reads/advisory; true accepted only for write, else E_USAGE. Never reject a read because an envelope serializes false. |
| reason, source_ref, directive, idempotency_key | None | None; inactive, even on unsupported command | Strict string; non-null on an unsupported context option is E_USAGE, including empty string. Supported empty strings remain empty and follow existing validation/gates; they are not inferred authorization. |
| transport/delivery options | Default execute/inline-or-reference policy | E_VALIDATION when a structured option is supplied null | Strict documented enum/object, no silent ignoring. |

Reason/source_ref apply to writes; directive only company writes; idempotency_key only where registry declares it. Advisory supports no active business context; false dry_run and null optional values are inactive. Human reason remains optional; an actual agent/system write still needs the core reason/directive gate. Existing core length constraints remain authoritative. If HTTP/Python currently accept an active unsupported context silently, correct that in the shared normalizer and include regressions across adapters; do not implement a new MCP-only error. Do not broaden normalizer work into business validation or reinterpret nested field nulls. Exact numbers, integers, fraction objects and decimal strings are never rounded/coerced by transport.

## 6. Binary bodies and complete JSON delivery (F1,F8)

Use bookflow_run's explicit transport branch for bounded byte frames, not a fourth tool. This keeps an actual MCP-only client capable of upload/download without requiring CLI, raw HTTP or local paths. No MCP resource capability is required in this revision. A future resources/read convenience could expose the same owned handles, but is not a prerequisite or alternate implementation choice here.

Transport op names: prepare, append, seal, execute, read, status, release. A prepare declares purpose command, input_json or binary_input, and immutable command/context for every purpose, including input_json; JSON input bytes are the only deferred argument. Returns an opaque random operation_ref before business execution. References are scoped to the host generation and internally bound to credential token ID, authenticated actor/principal, command, resolved company, canonical input/context digest and content purpose. Handle possession/session labels never replace fresh authority. Exact schemas and discriminated combinations below are published in run help and installed docs; no arbitrary host path or URI is accepted.

The transport branch is `{transport: {op, ...}}`, mutually exclusive with ordinary top-level arguments. prepare requires purpose and a command envelope; command requires exactly input or sealed input_ref, binary_input requires metadata input and declared body length/digest, input_json requires declared JSON length/digest and forbids input/input_ref. The latter's command/context is frozen before bytes arrive and may only execute that command. append requires operation_ref, integer offset>=0 and base64 data; seal requires only operation_ref and verifies the declaration. execute/status/release require only operation_ref. read requires operation_ref, channel (result or body), integer offset>=0 and integer length1..65536. Unknown or incompatible keys reject before effects; there are no arbitrary per-call limits or URLs. States are receiving → sealed/prepared → running → completed → released/expired; only command prepare starts prepared. append/seal apply only to receiving inputs; execute requires prepared/sealed, with repeated execute on running/completed observing the same execution. Reads of retained JSON are offset-addressable; binary reads are sequential with a retained last frame for identical retry. status describes state without advancing it. release is idempotent for an owned reference, requests cleanup and never cancels an accepted write. Out-of-state controls return E_USAGE with safe state; foreign/expired references use the indistinguishable error below. Transport context null/false rules remain §5; omitted required control fields or null are E_VALIDATION.

- command prepare fixes an ordinary command's arguments/selection and reserves response ownership; it does not run plan/apply. execute performs the actual command once in that host generation. A direct ordinary run is shorthand for prepare+execute; the adapter keeps the reference and includes it in any recoverable transport error. The published write journey uses explicit prepare so the client knows the reference even if the entire execute response disappears.
- input_json prepare/append/seal carries a valid input object's complete UTF-8 JSON bytes over bounded frames, with offsets, total length and SHA256. It is needed when a valid nested input exceeds a client's practical frame size. It is caller-owned transport content, not a business record. Final seal verifies the bytes; execute parses once into the identical object and passes it to core validation. A ref cannot be used as a binary body or by another credential. Temporary buffers for dry-run input remain nonpersistent; no persistent preview artifact is created.
- binary_input prepare receives the registered attachment add metadata and normalized context, including dry_run. It constructs HostedTransfer and runs existing transfer preparation/authorization before accepting body bytes. Each append carries at most CHUNK_BYTES=65536 decoded bytes (base64 in the MCP JSON frame); proxy/host decode only that frame and stream bytes to InputBody.write. Sequential offsets are checked; an identical retry of the last acknowledged chunk is acknowledged without double-appending, differing data/offset rejects. seal validates declared total/digest using the accumulated bytes without posting or prematurely consuming InputBody.complete; finish_input retains ownership of that completion call. execute calls finish_input once, handing the actual owned staged body to the host writer. No all-body base64 string, fake empty input, second attachment store or adapter business insert.
- Upload preview follows the same byte journey with dry_run=true and the existing no-persistent-stage InputBody; it hashes real bytes and returns the actual core preview. Real upload honors existing registered size/media/ownership/idempotency/hash checks. Metadata such as original_filename, media_type, record links and explicit fields stays in registered input, unchanged. Missing/mismatched body/context/command rejects before posting; reselection cannot redirect an existing body.
- attachment get execute invokes the registered output transfer and returns its exact business metadata plus a separate transport manifest. read obtains sequential bounded byte frames from that live owned transfer. Each frame performs HostedTransfer.check_output plus the full shared publication fence (§8); verify size/hash across the full stream, close on verified EOF/release/cancel/failure. No SQLite reader is held while waiting between chunks. The existing lease limits, deadlines and filesystem gates apply; resume of an expired binary lease is a fresh authorized attachment get, with matching immutable content digest, not an unguarded spool read. The installed client assembles/verifies bytes and publishes its local destination only after complete success.

For ordinary JSON, there is **no1MiB-input or8MiB-result rejection limit**. Input and result frame sizes are delivery thresholds, not limits on otherwise valid commands. Keep the full core result, including full-record list enumeration. Default inline delivery returns exact structuredContent and one JSON text rendering for ordinary-sized results. Above a documented inline threshold (256KiB proposed), or when delivery=reference is requested, return a manifest distinguished by _meta transport encoding, not a success-shaped truncated core object. The complete UTF-8 JSON result is then obtained with read frames, length+digest verification and one final JSON parse; the decoded object is exactly the same output/error as inline/CLI/HTTP. Never omit collection items, silently convert list to query, discard fields, or claim a manifest itself is the business output.

Result manifests carry operation_ref, content kind, total byte count, SHA256, completion/error flag, chunk size and expiry/recovery information. Chunk envelopes carry offset, bytes, next offset and complete. For binary commands the typed business metadata and body are separate content channels; if that metadata is large, it too has a JSON reference. isError follows the underlying command on both inline and manifest responses. Transport-control acknowledgements are explicitly transport state, never a claim that the command posted. Registry parity compares fully decoded command documents and, for transfers, full verified bytes as well.

Result/input buffers are private host transport resources, not audited business tables or credentials stores. For this increment retain completed results in host memory, never persist token secrets/passwords or result bodies to disk. Bound active operation count (host8, per-token2 initial defaults), backpressure with E_DB_BUSY before admitting new operations, and release active capacity only after actual worker/reader cleanup. Completed memory-only receipts do not occupy active execution slots, so routine successive commands do not exhaust two slots. Pending binary readers retain their existing lease ceilings; result retention has idle expiry and explicit release, with actual memory pressure reported safely rather than a fixed per-result size rejection. A completed result remains available for10minutes of inactivity; successful authorized reads/status renew that idle deadline, so a large result is not doomed by a fixed total-size or total-reading-time cap. Readers release when done; guide does not leave resources idle. Actual allocation/I/O failure is E_IO, not an invented invalid-command size restriction. Result-slot reservation precedes submission; no fixed byte quota rejects a valid command. Existing business attachment limits remain unchanged.

Operation refs survive stdio-process restart against the same host and token; new process sessions do not break content ownership. status/read retrieve the retained result without executing a command again. Repeating execute on the same prepared ref returns/rereads its one result or reports running, never runs plan/apply twice. This is bounded transport delivery deduplication, not a durable substitute for business idempotency keys. It is separate from JSON-RPC request IDs and from permanent conversion keys. The guide requires genuine business keys where supported.

If host restart, expiry, explicit release or memory failure loses a result, never resubmit an uncertain write automatically. Report unknown and recover through the command's documented idempotent replay/current show/history/audit; any oversized replay result is again available by frames. An operation without durable idempotency cannot promise its original receipt after a host crash: inspect resulting records/audit and decide explicitly. A lost one-time token secret cannot be reconstructed; the authorized operator identifies/revokes the issued credential and explicitly issues a replacement. Do not store the secret to pretend otherwise. This is the existing one-time-secret/crash boundary, not an MCP denial. Normal transport fragmentation, disconnection and adapter restart have a complete same-host result retrieval path.

## 7. Credentials, secrets and exact result/error semantics

Core permissions govern token issue, list/revoke and user set-password. Human self-service/admin rules and agent issuance denial remain unchanged. Return the authorized one-time secret in the actual successful command output; do not redact it as a transport policy or return it on denial/preview unless core does. Secret metadata informs display/log suppression, never permission. The configured authentication secret is never echoed automatically. Authorized output of a new secret is intentional command output, not the same as leaking the configured bearer. Tests explicitly distinguish these cases.

Never log credentials/hashes, sensitive inputs, result bodies or exception repr containing them; SDK failures must not dump arguments. Logs use correlation IDs, command names and safe error categories. Protocol content necessarily contains authorized requested data and may contain an issued secret: the client controls its confidential handling. No claim that all valid results are secret-free. Current path and cost-field redaction remains core-owned and is refreshed at publication. Client source_ref strings remain inert.

Inline success: isError=false and exact core object in structuredContent plus equivalent JSON text. Bookflow error: isError=true and identical redacted {code,message,details}; referenced delivery preserves the same rule after full decoding. No generic ToolError that loses structured conflict details, no success flag on a failure, no committed-output narrowing or automatic correction of input. Preserve warnings, no-op/replay/dry_run flags, IDs, versions, Row21 latest-writer/unknown history, E_PREVIEW_STALE, E_PARTIAL_WRITE and partial outcomes exactly.

Every failure to establish a valid result **after submission** is uncertain: timeout, disconnect, truncated/invalid JSON, wrong content type, incompatible version/shape, failed digest, invalid manifest, response size/frame failure, missing result, or SDK serialization failure. The adapter-generated error must carry outcome=unknown and the operation_ref when available. A compatibility error discovered after send is not evidence of non-execution. Before submission use outcome=not_submitted only when established. A valid core error is preserved unchanged; its own partial-write semantics remain authoritative. Publication denial after a committed write is a new safe error with possible/known commitment metadata, not a forged rollback or the suppressed original receipt. Cancellation emits no late protocol result; documented status/recovery handles uncertainty.

Adapter-owned public errors, added to shared documentation without inventing new code strings:

| Condition | Code and stable details | Recovery |
|---|---|---|
| Bad envelope/frame/cursor/type | E_VALIDATION; fields, reason=malformed_transport or malformed_cursor | Correct arguments. |
| Unknown command/unsupported local lifecycle/active unsupported context | E_USAGE; command/argument/boundary where safe | Read help; local lifecycle stays local. |
| Catalog changed during paging | E_QUERY_STALE; scope=command_catalog, reason=registry_changed, restart=true, current_registry_digest | Restart catalog without cursor; no business query implied. |
| Host missing/incompatible bridge before send | E_VERSION_MISMATCH; supported_bridge_versions, received_bridge_version or null, stage=preflight, outcome=not_submitted | Upgrade/configure intended host; do not fall back. |
| Any incompatible/unusable reply after send | E_IO; operation=mcp_result, errno=null, reason, stage=post_submission, outcome=unknown, operation_ref when known | status/read then safe domain recovery; no autoexecute. |
| Missing/expired/foreign ref | E_RECORD_NOT_FOUND; record_type=transport, no existence distinction | status/recovery from retained receipt/domain; if execute was submitted, wrapper retains outcome=unknown. |
| Admission busy | E_DB_BUSY; stage=admission, outcome=not_submitted, retryable=true | Release completed resources/back off, same intended request. |
| Real transport allocation/I/O failure | E_IO; operation, errno or null, stage and outcome | Repair/recover; not a command size-limit error. |
| Current publication authority denied | E_UNAUTHENTICATED or E_PERMISSION from guard; stage=publication, outcome=unknown for a submitted write, no protected receipt fields | Reauthenticate/re-authorize; inspect with current rights, do not replay blindly. |

SDK malformed JSON/protocol methods/unknown MCP tools retain documented JSON-RPC errors. Unknown registered command is an E_USAGE tool result. The low-level handlers validate their own envelopes and use safe validation details without input values. Never catch cancellation into E_INTERNAL. A safe internal failure before dispatch may be E_INTERNAL; after submission it must also communicate unknown, never suggest retry is duplicate-safe.

## 8. Full authority and lifetime fence (F6)

The shared executor must establish authority at admission, inside the actual execution session after queue wait, and immediately before publishing **every** result: reads, writes, previews, advisory, replay, errors containing data, catalog/help, status/manifests and every content frame. Binary checks also use existing transfer ownership/digest checks. Authentication includes token expiry/revocation, active actor/principal, assigned principal and unsuspended integer epoch. The queued witness must turn401 and leave fax unchanged while ordinary authorized work remains identical.

A credential+company-visible check is insufficient. Extract a side-effect-free shared publication_authorize contract covering all facts relevant to the original command/result: current actor kind/hub-admin, effective memberships/roles/grants/denies/features where actually enforced, principal authority, company/org visibility, resource_requirements, input-conditional authorization, target ownership/self-vs-other rules and field visibility (including path/cost permissions). Reuse shared permission predicates; never parse authorization prose, invent MCP grants, or rerun plan/apply/replay to test authority.

At execution capture a PublicationPermit with the normalized command/context/selected IDs and the authority dependencies used by those predicates/projections. Inventory all commands and conditional field projections: each must use the common guard or an explicit pure publication guard for its extra requirements. Current-state checks run in a fresh read-only session at each publication. Conservatively suppress the entire stored document if a relevant authority dependency changed or cannot be re-established, even if the actor still sees the company; do not serve an old admin/cost-visible projection to a downgraded member. Static metadata needs current authentication only. This conservative guard may require a fresh read for a new projection, but must never execute an already committed write again. Unrelated ledger changes alone are not permission changes.

This is shared authorization extraction and regression work, not activation of unfinished granular Row7 policy. Include the same fence for ordinary HTTP/workbench result paths and owned transfers; test no adapter-specific privilege expansion. The builder must explicitly account for conditionally authorized commands/fields in the registry-wide matrix. An unaccounted permission dependency blocks integration rather than falling back to role-only publication.

Narrow exception: a successfully committed token revoke whose exact target is the authenticating token may return only its existing TokenRevokeOutput once to that already admitted call, if the caller was authorized at execution and the sole newly failing credential condition is that same operation's revoked_at change. Other active-user/principal/role/target permissions must still pass, using the original credential identity for this check. No arbitrary self-change, agent suspension, user deactivation, other-token revoke, password operation, unrelated write, later status read or subsequent call inherits the exception. For a lost self-revocation receipt, recover using a different currently authorized credential/core token list; the revoked token does not gain a recovery channel.

Publication linearizes at the fresh guard immediately before starting response/chunk send; do not await unrelated work between permit and send. A stream checks each frame and aborts on loss of authority. Bytes already sent cannot be recalled; documents assembled from multiple frames are not complete until final digest/EOF.
