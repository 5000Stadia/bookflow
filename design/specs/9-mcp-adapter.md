# 9 — MCP adapter implementation proposal

Status: ready for independent plan review; not approved or implemented.
Prepared 2026-09-05. Target and completion authority: main `design/intention.md`, Row9 and its agent/GUI cooperation criterion; `design/blueprint.md` §§4.4, 5, 15.3, 16, 17. Parent owns intention, goal, integration and closure. Payments remains the primary implementation stream. This increment adds no accounting command, payment behavior, ledger table or migration.

## 1. Chosen transport and scope

Implement `bookflow mcp` as a client-launched **stdio MCP server**, one configured Bookflow bearer token per process. It connects to an already running Bookflow HTTP host. The existing host continues to own the root lock, writer queue, reader admission, databases, validation and audit. Current GUI requests remain `interface=http`, `client_name=bookflow-workbench`; Row9 does not introduce or assert `interface=gui`. The adapter never opens a data root, starts `serve`, invokes CLI commands, uses the OS-login socket, or calls a company's plan/apply function directly.

The process exposes exactly three MCP tools: `bookflow_list_commands`, `bookflow_help`, `bookflow_run`. Add a small bearer-only JSON bridge to the existing host at `POST /adapters/mcp/{operation}`, where operation is `list-commands`, `help`, or `run`. The bridge receives the same argument object as the corresponding tool. Its execution operation calls the **same extracted hosted command executor** used by ordinary HTTP/workbench requests, ultimately `core.dispatch.execute`. List/help project the host's registry and documentation renderer. This bridge is ordinary Bookflow HTTP, not an MCP Streamable HTTP endpoint or a second business API. It exists to retain host-authoritative discovery and to establish `interface=mcp` on a dedicated server-controlled adapter entry.

Do not silently fall back to `/commands` (which records `http`) or offline execution when the bridge is missing. Report compatible-host requirements. Do not add an `X-Bookflow-Interface` override to existing routes. Ordinary HTTP must stay `http` even when its client label contains "mcp" or its caller sends a forged interface header. The dedicated bridge constructs its fixed MCP context server-side; neither its argument object nor nested business input may choose interface, actor or principal. The bridge's bearer grants exactly its ordinary Bookflow authority, never a new permission. Calling the bridge directly is allowed to that same bearer and is documented as an MCP-adapter invocation; `interface=mcp` is an entry-point attribution, not cryptographic proof that an LLM made the call.

Row9 delivers local agent-client compatibility, including a local stdio process connecting to an explicitly configured remote Bookflow host. Native remotely hosted MCP/OAuth discovery, legacy HTTP+SSE MCP transport, MCP resources/prompts/apps, sampling, elicitation, tasks, subscriptions and provider integrations are outside this increment. No NLP/chatbot, arbitrary shell, model provider, email, payment schema or automatic outbound delivery is added.

## 2. Verified protocol and SDK choice

Use the **official `mcp` Python SDK 2.1.1**, optional installation extra `bookflow-core[mcp]`, initially pinned to `mcp==2.1.1` with its transitive versions recorded in `uv.lock`. Do not add the unrelated standalone `fastmcp` distribution or copy v1 decorators/imports. GitHub's latest release and PyPI both report 2.1.1, published 2026-08-25, non-prerelease. The current official protocol is **2026-07-28**, not the older initialization-only protocol. [Official release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.1.1), [published package](https://pypi.org/project/mcp/2.1.1/), [current specification](https://modelcontextprotocol.io/specification/2026-07-28).

Choose SDK v2's low-level `mcp.server.Server` with its typed list/call handlers and SDK stdio runner. This is justified by exact registry schemas and explicit `CallToolResult` construction: Bookflow errors must retain their complete JSON document in structured content. The low-level server does not validate tool arguments automatically; validate the three envelopes explicitly with Pydantic, then let dispatch validate the selected command input. SDK Python fields use snake_case, while the SDK handles wire aliases/era differences. Do not handwrite framing or version negotiation. [Low-level API](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/).

Support and test modern `server/discover`/per-request metadata and the SDK's legacy `2025-11-25` initialize path against the same three tools. Advertise tools only, with no list-change promise. No dependence on legacy session identity for Bookflow authorization. STDIO stdout contains only protocol messages; diagnostics go to sanitized stderr, and EOF initiates exit. [STDIO binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [SDK legacy compatibility](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/).

STDIO credentials come from launch environment, which the protocol explicitly distinguishes from HTTP OAuth. Because the only MCP-facing transport here is stdio, do not advertise Bookflow's opaque token as an OAuth access token or claim MCP HTTP authorization compliance. Adding native Streamable HTTP would require a separately reviewed OAuth/resource-audience design. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

The published SDK requires Python>=3.10, Pydantic>=2.12, AnyIO>=4.9 on Python3.12, and `httpx2>=2.5.0`; Bookflow requires Python>=3.12 and currently locks Pydantic2.13.5/AnyIO4.15.0. Use `httpx2.AsyncClient` for the bridge, declare it explicitly in the MCP extra if imported directly, and pin the resolver-selected version in the lockfile. Verify its installed API in the isolated build environment. Keep existing HTTP test dependencies unchanged unless resolution requires a demonstrated adjustment. No SDK import during ordinary CLI startup or host startup; the pure JSON bridge does not need the optional SDK. Do not configure SDK OpenTelemetry exporters, auto-instrumentation or telemetry providers.

## 4. Launch and credential contract

Proposed invocation after separately installing the package and starting the intended host:

```text
bookflow mcp --url http://127.0.0.1:8765 --token-env BOOKFLOW_TOKEN --client-name bookflow-agent
```

A client configuration should use the absolute executable and an argument array, without a shell:

```json
{"mcpServers":{"bookflow":{"command":"/absolute/venv/bin/bookflow","args":["mcp","--url","http://127.0.0.1:8765","--token-env","BOOKFLOW_TOKEN"]}}}
```

`mcpServers` is a common client configuration convention, not an MCP wire requirement. The operator must configure the client's secret-environment facility to inject `BOOKFLOW_TOKEN` into this subprocess. Do not assume all clients inherit that variable, support `${...}` substitution, or use this exact config format. The official SDK subprocess journey must explicitly populate its child environment from the test's private token variable. No configuration example contains a real token. Document both installed-package and locked source-checkout launch with no runtime download/install on each tool invocation.

`--url` is required unless `BOOKFLOW_URL` is set. `--token-env` defaults to `BOOKFLOW_TOKEN`; its value is the environment variable's **name**, not a secret. Read the nonempty secret once at startup and keep it private to the process; token rotation means restart. No `--token SECRET`, token-in-URL, token-in-tool argument, token file auto-discovery, OS-login fallback or interactive password prompt. Update blueprint15.3's historical command-line secret example as part of integration, explicitly replacing it with this environment form.

Use a rootless standalone registry command, `bootstrap=True`, `local_only=True`, with a typed launch input. Add a narrow `stdout_mode="protocol"` descriptor allowed only for standalone launchers, or equivalent explicit lifecycle descriptor, honored by CLI and docs generation: no ordinary output/warnings renderer on EOF, no final JSON object, and no data-root/company/reason/dry-run/interactive/clear flags for launch. Missing optional dependency fails on stderr with installation instructions; `bookflow mcp --help` works without the SDK and does not initialize a root. Protocol mode must not inherit diagnostic behavior that writes to stdout.

One process = one token, one fixed host origin, one configured client label. No model-controlled URL, headers, token, actor, principal, data-root, session or request ID. Use a private HTTP client with `trust_env=False`, no automatic redirects, no proxy inheritance, no cookies, no automatic retry, TLS verification enabled. Permit plaintext only to numeric loopback addresses; use verified HTTPS for other hosts. Reject URL userinfo/query/fragment and malformed base paths before reading/sending the token. A configured origin is an explicit trusted Bookflow destination; redirects never receive credentials. Do not fetch `$ref` URLs, media URLs, source_ref URLs or documentation links while executing a tool.

`client_name` is launch configuration; default `bookflow-mcp`. `client_version` identifies the adapter package. Treat MCP peer clientInfo as informational, never as identity or authority. Context is constructed on the host with `interface=mcp`, token row ID as the Bookflow session ID, a fresh Bookflow request ID per call, actor/principal from the verified credential, and supplied reason/directive/source_ref/idempotency context only. Record the peer label separately only if an existing non-authority context field can represent it without changing this rule.

The bootstrap token currently belongs to its issuing human. Public creation of agents/principal assignments is absent. Docs must say so. A configured human token remains `actor_kind=human` even though an agent application uses it; an already provisioned eligible agent token remains `actor_kind=agent` with its assigned `on_behalf_of`. Do not manufacture a principal, impersonate an agent, or add identity provisioning in Row9. Tests may use the existing labelled disposable authority fixture to exercise true-agent cases.

The host bridge accepts only bearer-kind credentials, never browser cookies or session secrets in the bearer header. Resolve credentials before command/company/availability diagnostics. Bind startup to bridge contract version1; missing/unsupported bridge yields actionable `E_VERSION_MISMATCH` without a fallback. The bridge returns its contract version and registry digest with catalog/help; metadata always comes from this live host, even if its application build differs from the launcher.

## 5. Three-tool contract and discovery policy

All tool argument objects forbid unknown top-level fields. JSON primitives retain their types; omitted and explicit null stay distinct. Business `input` is an object and is forwarded unchanged, never flattened or coerced by the MCP layer.

| Tool | Arguments | Result |
|---|---|---|
| `bookflow_list_commands` | Optional `prefix` (canonical noun/name prefix), `limit` integer1..200 default100, `cursor` | `commands`, `next_cursor`, `registry_digest`, `bridge_version`. Every command appears across pages, including unavailable commands marked with their transport boundary. Each entry: canonical name, description, scope, kind, required-role/authorization description, MCP execution mode. No individual command schemas here. |
| `bookflow_help` | Required canonical `command` | Name/description/scope/kind, `documentation` (single-command generated Markdown), full input/output JSON Schemas including local `$defs`, output field descriptions, command+infrastructure error codes, accepted context fields, preview/idempotency/version-source/transfer/stream metadata, MCP execution mode/reason, registry digest. |
| `bookflow_run` | Required `command`, required object `input`; optional `company`, `reason`, `directive`, `source_ref`, `idempotency_key`; `dry_run` strict boolean defaultfalse | Exact core success output object or exact redacted Bookflow error document. |

Canonical command strings use spaces (`journal post`, `sales-receipt show`). Do not add natural-language matching or guess aliases. Any dotted-name support must reuse the existing HTTP name conversion and return the canonical name; the documented initial tool contract requires canonical names.

Catalog/help are **authenticated static product metadata**, available equally to all valid bearer identities. They are not permission-filtered business data and are not a promise that a particular user may execute a command. Do not invoke its plan to produce help. Include stated authorization requirements, never a guessed `can_run` based on incomplete role information. No company list, record sample, real identifier, per-company feature state, custom field choices, principal name, filesystem path or secret value is inserted into static examples/schemas. Runtime choices are obtained through ordinary authorized list/query commands. Static command names do not disclose another company's existence.

There is no company context on catalog/help and no mutable selected company in the MCP process. Discover visible companies using `bookflow_run(command="company list", input={})`; pass an explicit company on each company-scoped run. Omission returns the shared no-company error, even when one company is visible. Hub commands reject a supplied company through dispatch. Company strings use existing resolution semantics (ID, unambiguous name, Organization/Company); examples prefer returned IDs. Hidden and nonexistent targets follow the same core error behavior; suggestions contain visible companies only. Never obtain all companies and filter in the adapter.

Catalog paging is deterministic by canonical name. Cursor contains only versioned registry digest/filter/position, with a bounded validated encoding and no credentials. Reject malformed or changed-registry cursors and require restart; do not keep a per-user discovery cache. No business authority is encoded in a cursor. Build metadata through a shared pure descriptor used by MCP help/docs (and reused by OpenAPI where fields coincide), with a test comparing those projections.

MCP's three protocol tool descriptors themselves are static and contain no company data; `tools/list` may publish them without a live business lookup. Every catalog/help/run tool invocation still authenticates against the host. This distinction lets a client discover how to recover from authentication failure without receiving company data. List/help annotations are read-only; run is conservatively potentially destructive, not read-only or generally idempotent. Actual command metadata explains which invocations have previews/retry keys. Annotations never authorize a call. [MCP tool semantics](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

## 6. Routing and secret/stream/attachment boundaries

Use one explicit execution-mode descriptor projected from registry metadata; enforce the same mode at the host bridge, never only in the stdio process.

- Normal routed commands execute through shared dispatch. Read, write and advisory retain their existing lifetime; advisory is not mislabeled read-only.
- `local_only`/standalone commands are listed/helped but `run` returns `E_USAGE` identifying their operator-local boundary. Current examples: `init`, `serve`, `company use`, `docs generate`; the new `mcp` launcher is also not recursively executable.
- `streams=True` allows the ordinary finite JSON call (`audit tail`, `hub audit tail`). `--follow` is a CLI lifecycle option, not a command input or an MCP stream. Help explains bounded polling and exact `after`/`next_after`/`high_water` semantics. No background watcher, subscription or held database reader is created.
- `transfer is not None` is unavailable through `run` for both real and preview calls: existing `attachment add/get` require their actual binary transport. Return E_USAGE before staging/reading bytes, with static instructions to use the existing authenticated transfer API or local CLI/Python streams. Do not accept base64, a local filename, URL fetch, MCP resource URI, or synthetic empty body as a substitute. Attachment metadata/link/unlink/list and note/activity commands remain available under ordinary permissions. Do not return unauthenticated download URLs or embed documents into MCP context.
- **Credential input/output commands are operator-only on MCP.** Add/complete explicit `secret` metadata on sensitive input/output model fields (notably `TokenIssueOutput.secret`); recursively derive a `secret_io` execution boundary. Current `token issue` and `user set-password` remain discoverable but reject through MCP, including dry-run. Token list/revoke retain their ordinary authorized behavior and never disclose the configured secret. This is a documented transport limitation, not a new credential-issuance permission or a change to CLI/HTTP. An unavailable command must not execute and then redact its receipt. Future secret-bearing commands fail the same policy automatically.

Never log authorization headers, credential hashes, argument bodies, result bodies or raw exceptions containing them. Return core redacted errors; generic internal/connection errors carry only a generated correlation ID and safe explanation. SDK logging must not serialize tool parameters or context on exceptions. Test with canary secrets in launch environment, rejected arguments, unusual HTTP errors, stderr, stdout, logs and audit snapshots. No outbound telemetry or secret copies into test receipts/docs.

## 7. Result parity and recoverable errors

Construct results explicitly. On success: `isError=false`, `structuredContent` equals the core output object, and one text content block contains deterministic JSON of that same object. On a Bookflow failure: `isError=true`, both channels contain the identical `{code,message,details}` document, without adding a success envelope or turning it into a generic SDK exception. Publish a broad object output schema for run; its command-specific output schema lives in help. Preserve all warnings, dry_run/no-op/replay flags, IDs, cursors, fingerprints, versions, conflict attribution and partial-write details. Do not revalidate committed output into a narrower adapter model and silently drop fields. [Structured output](https://py.sdk.modelcontextprotocol.io/servers/structured-output/), [SDK error distinctions](https://py.sdk.modelcontextprotocol.io/servers/handling-errors/).

Protocol malformed JSON, missing protocol fields and unknown MCP methods remain SDK JSON-RPC errors. Unknown MCP tool uses the SDK's documented unknown-tool/invalid-params error. Invalid **Bookflow** command/envelope/input is a structured tool error: E_USAGE, E_VALIDATION, E_CONTEXT_IN_INPUT, etc. Validate envelopes with safe Pydantic error conversion that excludes raw input values. Do not catch cancellation into E_INTERNAL. Do not map permission or conflict errors to HTTP/network failures.

Host HTTP bridge uses existing Bookflow status/error mapping. The stdio process distinguishes HTTP error documents from non-JSON proxy failures; it never echoes an HTML error page, credentials, full URL or response headers. Transport failure/timeout gives E_IO with `details.outcome="unknown"` for a submitted run and actionable re-read/retry advice; it cannot claim rollback. Preflight failures can identify `not_submitted` only when no request was sent. An unrecognized bridge response or incompatible bridge version stops safely; do not retry automatically.

`dry_run` reaches dispatch, including its rejection on read/advisory commands. Preview is not a reservation or permission bypass. Carry the caller's preview fingerprint in `input`, never invent or refresh it automatically. Expected versions remain caller-provided command input; retain Row21's strict financial conflict/unknown-history wording. Idempotency keys and permanent business conversion keys are distinct: pass both where declared, do not generate them from JSON-RPC request IDs, and do not attach an idempotency key to a command that rejects one. Retries use the same authorized intent, same key and same original input; conflicts require inspection/re-read. Money, exact numeric strings, integer minor units and fractions are never converted through float.

## 8. Read/write lifetime, cancellation and revalidation

The adapter stores no Bookflow Session or loaded actor across calls. At most eight in-flight bridge calls per MCP process; bounded request body1MiB and decoded host response8MiB, with no truncation or pagination rewriting. Limits are transport limits documented in help. A response too large after a write may already follow commit and must report outcome unknown, never not-submitted. Default connection timeout5s and total tool timeout60s, configurable at launch up to300s. No progress notification extends that maximum. These are proposed adapter limits, not measurements or changes to business command limits.

Shared execution rules:

1. Authenticate at host admission before diagnostics, then verify the same original credential again in the execution session. For a read/preview, use its admitted read-only hub snapshot to establish actor/binding and execute. For a write/advisory, verify in the writer callback before dispatch and before any plan/write. Rebuild context from that verified row. Revocation/expiry/principal/epoch change while waiting must reject; stored user ID alone is insufficient.
2. Membership and record checks run at execution, including replay. Do not cache a successful `authorize` or use an old visible-company list. Recheck the credential and selected-company visibility in a fresh read just before publishing a completed read; discard output if authority was lost. Define publication's linearization point as that final check; bytes already delivered cannot be recalled. Do not claim a later revocation undoes a committed write. Preserve the receipt for an authorized self-revocation, without authorizing a subsequent call.
3. Reader close and `reader_done` occur in the worker's `finally`, including cancellation, network error, host shutdown and folder-gate refusal. Async cancellation must not close a SQLite connection owned by another thread. Accepted writer jobs remain host-owned through commit/rollback and `_leave_clean` after the caller stops waiting.
4. Before submission, cancellation prevents sending the bridge request. Once accepted, cancelling the MCP request closes/cancels its HTTP wait and suppresses further protocol output. It does **not** promise to dequeue, interrupt SQL, roll back, compensate, or stop a financial write. The host can finish the accepted request. Reconnect/read or replay with the same eligible key to determine outcome. SDK framing/cancellation suppression stays authoritative. [Protocol cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation).
5. EOF/SIGTERM closes adapter admission and outstanding HTTP clients and exits without stopping the Bookflow host. The host alone drains admitted workers, readers and commits on its own shutdown. Any cancellation worker still finishing retains responsibility for releasing resources; neither process returns a pooled connection mid-job. Bounded MCP admission at the host must retain slots until workers finish, including disconnected requests, so repeated cancellations cannot create an unbounded hidden queue. Use a host-wide MCP cap8 and per-credential cap2, reject excess with E_DB_BUSY; release in the worker's finally, not the proxy's cancellation handler.

Credential liveness refresh is existing unaudited host metadata maintenance. Discovery/preview/rejection tests distinguish that allowed hub `last_used_at` activity from business, revision, posting, idempotency and audit mutations; do not claim HTTP authentication is literally zero disk writes. Invalid credentials must not refresh. Company data and attributed business/audit state remain unchanged on rejection and ordinary preview.
