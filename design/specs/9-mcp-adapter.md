## 1. Architecture and preserved authority

One client-launched stdio process exposes bookflow_list_commands, bookflow_help and bookflow_run using one configured existing Bookflow bearer. It talks to the existing host through bearer-authenticated /adapters/mcp bridge endpoints. The host retains the root lock, writer queue, readers, command registry, accounting engine and audit. The adapter does not start another host, acquire a bookkeeping root lock, invoke shell/CLI commands, or authenticate as its OS login.

Extract a shared hosted executor from adapters/http/app.py, calling core.dispatch.execute, and shared current-credential/publication guards. Use this for HTTP, workbench and the MCP bridge. Binary execution uses core.transfers.HostedTransfer, InputBody, TransferLease and existing command transfer.prepare/validate_resource, not a second attachment store or simulated JSON post. Add bridge operations for leased byte input/output and complete JSON result delivery, described in §6. All permission checks are shared command checks; transport handles never grant company/command access.

The host's dedicated MCP entry fixes interface=mcp. Existing HTTP stays http even if a caller sends an interface header or client label "mcp". Current human workbench activity remains interface=http, client_name=bookflow-workbench; do not claim interface=gui. MCP attribution names the adapter entry, not proof that a model originated the request. Direct invocation of this bearer-authenticated bridge has the same permissions and attribution. No caller-supplied actor/interface/principal override and no fallback to the ordinary HTTP route (which would misattribute MCP work).

Normal routed commands, including authorized token issue and user set-password, retain their exact rights, inputs, previews and outputs. No secret_io exclusion, silent secret removal, or transfer exclusion exists. Existing local_only/standalone and CLI --interactive/--follow lifecycle boundaries remain explicitly documented; they are not new MCP business denials. Native OAuth/Streamable HTTP MCP, prompts, sampling, elicitation, tasks, subscriptions and external sends remain outside this plan. The native bridge is Bookflow HTTP; it does not claim MCP OAuth compliance.

The current official protocol is **2026-07-28**, not the older initialization-only protocol. [Official release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.1.1), [published package](https://pypi.org/project/mcp/2.1.1/), [current specification](https://modelcontextprotocol.io/specification/2026-07-28).

Choose SDK v2's low-level `mcp.server.Server` with its typed list/call handlers and SDK stdio runner. This is justified by exact registry schemas and explicit `CallToolResult` construction: Bookflow errors must retain their complete JSON document in structured content. The low-level server does not validate tool arguments automatically; validate the three envelopes explicitly with Pydantic, then let dispatch validate the selected command input. SDK Python fields use snake_case, while the SDK handles wire aliases/era differences. Do not handwrite framing or version negotiation. [Low-level API](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/).

Support and test modern `server/discover`/per-request metadata and the SDK's legacy `2025-11-25` initialize path against the same three tools. Advertise the three tools with no list-change promise; file sidecars and intent recovery are part of bookflow_run, not extra tools; byte framing is private adapter/host work. No dependence on legacy session identity for Bookflow authorization. STDIO stdout contains only protocol messages; diagnostics go to sanitized stderr, and EOF initiates exit. [STDIO binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [SDK legacy compatibility](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/).

STDIO credentials come from launch environment, which the protocol explicitly distinguishes from HTTP OAuth. Because the only MCP-facing transport here is stdio, do not advertise Bookflow's opaque token as an OAuth access token or claim MCP HTTP authorization compliance. Adding native Streamable HTTP would require a separately reviewed OAuth/resource-audience design. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

The published SDK requires Python>=3.10, Pydantic>=2.12, AnyIO>=4.9 on Python3.12, and `httpx2>=2.5.0`; Bookflow requires Python>=3.12 and currently locks Pydantic2.13.5/AnyIO4.15.0. Use `httpx2.AsyncClient` for the bridge, declare it explicitly in the MCP extra if imported directly, and pin the resolver-selected version in the lockfile. Verify its installed API in the isolated build environment. Keep existing HTTP test dependencies unchanged unless resolution requires a demonstrated adjustment. No SDK import during ordinary CLI startup or host startup; the pure JSON bridge does not need the optional SDK. Do not configure SDK OpenTelemetry exporters, auto-instrumentation or telemetry providers.

## 4. Standalone launch, configuration, company and provenance

Install the optional extra, start the intended host separately, inject a secret through the client's environment facility, then launch an absolute executable without a shell:

    /absolute/venv/bin/bookflow mcp --url http://127.0.0.1:8765 --token-env BOOKFLOW_TOKEN --client-name bookflow-agent

--url overrides BOOKFLOW_URL; --token-env names a variable and defaults to BOOKFLOW_TOKEN. No secret argv flag, token URL, credential in tool arguments, password prompt, automatic token issuance or OS-login fallback. Read the secret once; rotating it requires restart. A client must explicitly inject the variable if its subprocess launcher filters inherited environment; do not assume ${...} interpolation in client JSON. The installed guide supplies the exact supported client configuration and SDK subprocess environment construction.

One private HTTP client, fixed origin, trust_env=False, redirects/retries/proxy inheritance disabled, no cookies, verified TLS; plaintext only numeric loopback. Reject URL userinfo/query/fragment before reading/sending credentials. Never fetch a source_ref, schema $ref, business attachment filename or model-supplied URL. Only the separately declared, launch-allowlisted transport file fields below authorize client-side file access. No SDK telemetry/exporter configuration. Missing SDK or missing/empty launch token, malformed launcher options (not deferred company-selection config), or invalid launch values fail before protocol startup: nonzero process exit, safe stderr, no stdout. --help needs neither SDK nor root. A syntactically configured but invalid/expired token, stopped host or incompatible bridge does NOT kill startup: SDK discovery/tool listing works, and tool calls return structured configuration/auth errors. A restarted host can therefore recover without restarting the adapter; a changed token requires adapter restart. Contract compatibility is checked before each first submission to a host generation, not as a mandatory startup connection.

Register a lazy standalone launcher with protocol-owned stdout: no ordinary result renderer on EOF, no JSON receipt after the last MCP frame. Its output lifecycle descriptor is explicit and valid only for standalone commands. Reject inapplicable launch dry-run, interactive, reason, company and JSON-render flags with E_USAGE; do not confuse a process's configuration with a business command call. EOF/SIGTERM stops adapter admission and closes its HTTP work, not the Bookflow host.

### Company fallback (F3)

For each company-scoped execution: non-null company tool argument first; otherwise nonempty BOOKFLOW_COMPANY from the **stdio launcher's machine/process**; otherwise default_company for its actual OS login from that machine's selected Bookflow config. Use the same extracted selection helper and source labels option/env/default/none as CLI/Python. A present higher-precedence value that fails resolution never falls through. Hub-scoped calls ignore environment/default selection but reject an explicit non-null company.

The launcher accepts --selection-root solely for the fallback's read-only configuration source; precedence is that option, launcher BOOKFLOW_DATA_ROOT, then the same platform default used by CLI. It creates nothing there, acquires no writer/root lock, migrates nothing, and opens no company database. Use Config.load's existing read-only pending-projection handling where applicable. This narrow local config read replaces the earlier draft's blanket "no data root reads" claim. A missing config/mapping supplies no default; malformed/unreadable config returns shared E_CONFIG_INVALID only when that fallback is actually needed. Read the fallback per call, so an operator's local company use change is observed. Remote host environment, host service OS login and host default company never supply the remote MCP caller's implicit selection.

Local OS mapping supplies a selection preference only, never authentication. Even if it belongs to a more privileged local human, the selected company must resolve on the remote host under the bearer. Preserve ambiguity/not-found/visible-only suggestions and details.source. Unknown or hidden local defaults cannot grant remote access. Explicit company bypasses unnecessary local config reads. Frozen command/transfer preparation stores the selected company and source for that operation; a later environment/default change cannot redirect its chunks or execution. Test distinct caller/host defaults and roots, absent config, malformed fallback and high-precedence inaccessible selection.

### Process and client provenance (F5,F15)

Generate one fresh ULID at stdio process start and use it as Bookflow session_id for every command it initiates. Two processes with one token and a restart must have different sessions. Keep credential token ID separately in the host's internal authentication record; never use it as the MCP process session. Generate a fresh request_id on the host for each actual command execution; stream/status calls are transport activity, not extra business executions/audit events.

client_name is the configured launcher label, client_version its installed package version, client_host the launcher machine hostname. The launcher sends these and its process session through a fixed versioned provenance envelope/header set, separate from model tool arguments. Host validates types/lengths and normalizes this informational metadata. It is self-reported client provenance, not an authenticated machine identity; direct HTTP bridge callers can claim labels/session strings and gain no rights. Credential/principal/company authorization, handle ownership and replay protection must never depend on trusting those labels or session IDs. MCP peer clientInfo remains informational and does not replace the configured Bookflow label. Interface is always constructed by the host route, never taken from provenance.

Catalog/help are authenticated static product metadata, the same for all valid tokens. ## 6. Delivered file handling, one intent, bounded transport (F1,F8,F17–F20)

This section replaces revision2's public prepare/append/seal/read byte protocol. The delivered `bookflow mcp` launcher is the file client; there is no undisclosed agent-run script or required client plugin. Models choose a registered business command, its ordinary metadata/context and an actual permitted business-file path. The launcher reads bytes, counts/hashes them, streams them, verifies completion and publishes a destination. The host continues to execute the same registered transfer command through HostedTransfer. Only the three MCP tools are exposed. Models never manufacture hashes/base64, advance byte offsets or reconstruct files.

### Calling-machine file authority and portability

Launch accepts repeatable `--input-dir PATH` and `--output-dir PATH`. They name existing, explicit directories on the launcher machine, never the HTTP host. They authorize only business-file access within those directory capabilities. Neither is inferred from selection-root, home, current directory, company folders, tool arguments or MCP client's claimed roots. Omitting input directories disables local file reads; omitting output directories disables local file writes, while ordinary inline JSON works. A complete attachment-capable installation configures both as part of the literal installed setup. The parent supplies the permitted receipt path to the blind agent; no transfer recipe accompanies it.

Limit configuration to16 input and16 output directory handles per launcher; these are explicit resource capabilities, not per-file or business size limits. Keep a handle to each approved directory for process lifetime. File arguments are absolute paths lexically beneath one approved directory; relative paths are rejected, so no working-directory or alias lookup can change their meaning. Only the operator/task briefing supplies actual permitted business-file paths; authenticated static command help describes this syntax without enumerating local directories. Reject empty segments, dot/dot-dot traversal, NUL, URL syntax, unconfigured drives/UNC paths, device/FIFO/socket/directory inputs and any symlink component. Do not use resolve-then-open or a string-prefix check as the security boundary. Walk components relative to held directory descriptors with no-follow opens, verify regular-file identity with fstat, and operate on that descriptor throughout. Reject multi-link input files to avoid using hard links as a way to import another file; dedicated operator-owned inboxes must not be writable by other users. A supplied basename in business input is presentation metadata and never a path to open.

Output uses a private 0600 exclusive temporary in the opened destination parent, then no-replace atomic publication after full size/digest/final-result verification and a fresh host publication check in the original response’s terminal completion. Reject existing destinations, including symlinks/hard links; never overwrite. Close and remove only this operation's verified temporary inode on failure. Parent-directory replacement races cannot redirect a descriptor-relative open; recheck ancestor identities before publication and fail if the approved directory tree changed. Do not list neighboring files, recursively scan directories or expose local rejected-path details to the host. Operator setup must choose dedicated business exchange directories, not a bookkeeping/credential/system root. The adapter never creates a broader allowed directory or changes permissions on supplied source files.

The concrete initial implementation uses the Python/POSIX directory-descriptor and no-follow operations already used by core.transfer_paths.atomic_output, strengthened for the allowlisted ancestor walk. Deliver and test on Linux and macOS; Windows users use the packaged launcher inside WSL with explicitly configured WSL directories. Native Windows is not claimed: reparse points and lack of the same dir_fd operations require a separately tested handle-based backend; unsupported filesystem/platform capabilities fail when configuring those file capabilities, never fall back to unsafe path opens. No native-Windows file capability is advertised; ordinary stdio JSON support is a separate SDK/platform question. This is a stated portability limit of the delivered file mechanism, not a command/secret permission exclusion. Existing generic MCP clients need only standard stdio tool calls. [Python filesystem APIs](https://docs.python.org/3/library/os.html), [Microsoft reparse-point boundary](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points).

### Ordinary tool contract and automatic delivery

`transport` on a new command accepts only `input_file`, `output_file`, `input_json_file`, `result_file`, and `prepare_only` (strict boolean, default false). Each file option is a nonempty absolute path string; explicit null is E_VALIDATION. input_file is legal only for a registered binary-input command, output_file only for binary output. input_json_file replaces the input object for any command and carries the exact JSON object, distinct from attachment body bytes; it never changes business field semantics. Authenticate/admit the host command and known scope before the launcher reads that file; input-conditional authorization necessarily follows parsing its bytes and still precedes business execution. Binary body preparation additionally validates the complete metadata before body reads. result_file explicitly requests the complete JSON output/error document as a user-owned file instead of inline protocol content. Incompatible/unknown fields reject before submission; false prepare_only is inactive. No caller-supplied size/digest/chunk/URL/host-file parameter exists.

A normal attachment add takes its usual target, original filename, media type and caption in input and `transport.input_file` outside it. The launcher authenticates/prepares with the host and receives current authorization/limit before reading body bytes. It opens the permitted regular file, streams bounded chunks through the owned upload, and computes actual size/SHA256 while the host independently computes them. Finalization compares both and repeats all transfer/context/target authorization before finish_input. Detect local file identity/size/mtime change across the read; reject rather than silently upload a moving source. Actual received bytes, not stat or declared Content-Length, enforce the existing company limit capped at100,000,000 bytes. Preview follows InputBody's no-persistent-stage path while hashing actual bytes. Deliberate posting after preview is a new intent with its business key/fingerprint and a new authorized file read.

Attachment get automatically streams to transport.output_file, or generates a collision-resistant basename beneath the first configured output directory if omitted. It requires that output capability before execution. It uses HostedTransfer output authorization/digest checks for each chunk and a final publication check in the original response’s terminal completion; the launcher verifies bytes plus terminal result before publishing the local file. Typed business metadata is unchanged in structuredContent; `_meta.bookflow_transport` separately reports the client destination, actual digest/size, completion and recovery reference. Those paths are local delivery information, not business metadata/audit fields. A failed download never reports a complete output file. Authentication loss before local publication deletes the private partial; already delivered files are caller-owned data and cannot be recalled.

Ordinary JSON stays exact inline structuredContent plus equivalent JSON text by default, with no1MiB-input/8MiB-output exclusion. The host streams complete serialized JSON to the launcher; SDK serialization may require a full object for inline MCP output, so the installed docs also expose result_file for large machine-readable results. With result_file the delivered launcher incrementally writes and verifies the entire core JSON document, then atomically publishes it; the tool returns a clearly tagged delivery receipt, never a truncated business success. isError and terminal flags reflect the actual underlying document. The same three-tool recovery branch can inspect a delivered result's JSON values by JSON Pointer with bounded item continuation (complete arrays have count/next cursor), without asking the agent to process raw bytes. Inspection is explicitly navigation of the delivered full document, not a substituted business list/query or a reexecution. File delivery/inspection preserve every field and exact number. Valid large inputs may similarly use input_json_file; no model-written hashes or private helper are required. Full parity compares the complete JSON artifact as well as inline output, not only an inspection page.

Result files are explicit caller-requested output artifacts, like a CLI output sink, not host credential/result storage. They may contain authorized secret command output; the operator controls the private destination and cleanup. Do not automatically persist inline secrets. Previews create no host business/config/audit/staging artifacts; an explicitly requested client preview report is the caller's output, not a persistent preview record.

The private HTTP bridge owns machine framing; models see none of it. Use versioned intent admission and a continuous transfer response with typed channel records (business JSON, binary body, terminal completion/error), each carrying at most65536 payload bytes. Business JSON, including oversized metadata, is itself streamed across records, never stuffed into a bounded HTTP header. The terminal record carries channel byte counts/digests, actual error/completion state and recovery metadata; its fixed transport fields must fit one record, while arbitrary business/error details travel in the streamed JSON channel; unexpected order, duplicate terminal, missing terminal, length/digest mismatch or incompatible version is an invalid result. Input body transport is raw streamed bytes on the admitted intent with an explicit end/finalization handshake; no JSON base64 upload. Reuse existing transfer framing/ownership machinery where it fits, but no existing small result-header bound may narrow valid registered output. This is private Bookflow transport encoding; MCP wire framing/versioning stays entirely with the official SDK.

The writer's database session closes and writer queue is released before any slow result streaming; a separate admitted delivery owner holds only the authoritative output/permit and transport slot, never a SQLite session. Pure publication rechecks acquire/close fresh short readers before each output record and terminal record. A terminal permission check on the original call is the final host publication boundary, including the narrowly allowed self-revocation receipt; do not turn that exception into a new HTTP request authenticated by a revoked token. The launcher publishes a verified destination immediately upon validated terminal completion, with no intervening unrelated work. Later inspection or recovery is a new request and always needs current ordinary authentication.

For streaming JSON validation/inspection use the maintained `ijson` parser in the optional MCP extra, pinned initially to3.5.1 (published package requires Python>=3.9), with low-level events and use_float=False. Confirm the installed backend preserves large integers, decimal tokens, escapes and nested object/array keys; never silently convert money to float or emit Decimal as an unexpected JSON string. Use event-level traversal for JSON Pointer, not dotted-prefix guessing when a field contains a dot. The core's own serialization remains the output authority. Library/lock integration is implementation work, not performed for this plan. [Maintainer API](https://github.com/ICRAR/ijson), [published package metadata](https://pypi.org/project/ijson/3.5.1/).

### One frozen intent and recovery identity (F17)

Every new call with command+input creates one random intent_id under one host generation; direct calls and prepare_only use the same mechanism. The host binds it to the authenticated credential token ID, actor/principal, resolved company/source, command and normalized context. Input/body digests are finalized exactly once during the continuous authorized receive phase before the intent becomes ready; no execution is possible with an unsealed digest. The ready intent has immutable input/body identity. The launcher gets its operation_ref before any business submission; prepare_only returns it before execution for callers needing recovery even if the entire future tool reply is lost. Selection, context and bytes cannot be edited through a reference.

Recovery uses `{operation_ref: R, action: execute|status|release|inspect, ...}` instead of command/input/context. Alternate spelling `input_ref: R` is accepted only as an exclusive alias of operation_ref in this branch; it addresses the SAME intent and creates no object, execution, reference count or independent release right. Supplying either reference alongside a new command/input/context/file input rejects E_USAGE; do not copy bytes from an old intent into a newly prepared executable. execute after submission only observes/returns the original running/result state. Switching reference spelling or access route cannot submit twice. A deliberately new intent requires a new command envelope and fresh input/file read, and is explicitly described as new work; core idempotency/permanent keys still govern deliberate retries of one business effect. Transport identity is neither a durable business key nor inferred from equal bodies.

Release invalidates the whole intent and every alias, not one alias's buffer. Before submission it prevents execution and cleans its input/reservation; after accepted submission it abandons delivery but cannot close writer-owned resources or undo the command. No released/expired reference can create or resurrect execution. Host generation/credential binding and fresh full authority apply to recovery; client-supplied session/provenance never proves ownership. References survive launcher restart only to the extent the same host has retained that intent/result; launcher-local partial files are not remotely owned staging and are never adopted from arbitrary paths.

Recovery action-specific fields: status/execute/release take only the reference and action; execute may select result_file/output_file delivery destinations, never change frozen input. inspect takes a reference, JSON Pointer (empty means root), and optional bounded page/cursor; it reads a verified retained/delivered result through the launcher with fresh host authority, never executes. A pointer into a scalar returns that exact value; an array/object page carries explicit next cursor and total entries with no silent omission. Null/invalid pointers/cursors/types are E_VALIDATION; mismatched source digest/cursor is E_QUERY_STALE. Inspection may not report success if the full source document was not first verified. Reopen only the internally mapped descriptor-relative delivered file, verify its original file identity and digest, and revalidate the host publication permit before returning selected values; caller editing/replacing the file invalidates inspection. The permit lives in the same bounded/expiring host record, so loss/expiry disables inspection rather than bypassing authority. No raw filesystem access tool is introduced. Local delivered-result mappings have the bounded lifetime below; after expiry the file remains caller output but the adapter will not reopen it through a fabricated reference.
